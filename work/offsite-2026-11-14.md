## Offsite cameras — our own RTSP, motion-gated recording, batch upload (2026-11-14)

The requirement changed shape: these cameras are going **offsite on an LTE hotspot**,
so the design target is no longer "a live stream on the LAN". Measured from our own
captures: 720p runs at **0.97 Mbps ≈ 10.5 GB/day** (night ≈ 1.09 Mbps) and the
640x480 sub stream at **0.12 Mbps ≈ 1.3 GB/day**. A continuous upload over a mobile
uplink is therefore off the table, and CGNAT means nothing inbound, so the camera must
dial *out*. Recording is motion-gated and uploads happen in batches.

Decisions taken (user, 2026-11-14): **live view is best-effort via a camera-initiated
connection**; **relay the stock encoder first, replace it later**; **the camera pushes,
homelab never pulls**.

### `camrtsp` is now a real server, not just a protocol library

`tools/rust/camrtsp` — clean-room Rust, no crates, ARMv5TE (pure `Mutex`/`Condvar`;
no `AtomicU64`, the ARM926EJ-S has no `ldrexd`).

| piece | state |
|---|---|
| RTSP 1.0 server, TCP-interleaved + UDP, SDP, RTP, RTCP, sessions/fan-out | done, tested |
| pure-std RTSP **client** (`client.rs`) — pull H.264 + a-law from an upstream server | done, now wired |
| `--source client:HOST[:PORT][/PATH]` | **new**: the live path |
| `motion.rs` — compressed-domain motion detection | done |
| `rec.rs` — motion-gated segments + pre-roll + quota | done |
| `upload.rs` — resumable batch push to homelab | written, not yet wired |
| `pump:` (vendor encoder socket, `CAMRTSP1`) | waiting for the C shim |

`source::Hub` was a single slot and that was a real bug, not a nit: measured
end-to-end it **dropped all 8 keyframes of 375 access units** and the first frame of
every burst, so a session that joined mid-GOP never decoded. It is now a 48-frame /
4 MiB ring; `next(after)` walks it **in order** and resyncs on a keyframe only when a
reader has fallen off the end. `ended()` was added so a session knows the difference
between "no frame yet" and "the source is done".

Proven on the host, not on the camera: our client pulls from an upstream RTSP server,
our server re-serves it, `ffmpeg` reads **151 frames of 1280x720** through the chain,
and the detector fires on the real scene change in `main-20s` with a segment written
(`ffprobe` decodes 359 frames, 1280x720, no errors). 98 tests on `build-01`;
`camrtsp-arm` **3,463,012 B**, `Tag_CPU_arch: v5TE`.

### Motion detection without a vendor library

`libmpi_md.so` **was never shipped** on this device (`ak_md.h` is in the SDK headers;
every `.so` in the tree was scanned for `ak_md_init` — nothing). `libak_mt.so` is PTZ
motion *tracking*. Decoding 720p on an ARMv5 to diff pixels is not affordable, so v1
works on what the bitstream gives for free: **AU byte size, frame type, arrival
time**.

- Baseline = median of the last 30 **P-frame** sizes; an I-frame is ~10× a P-frame
  here (71 kB vs 7.1 kB) so mixing them would fire on every GOP.
* Evidence must clear a ratio (1.75x) **and** an absolute floor (1500 B), decays with a
  2 s half-life, triggers at 1.0 → one isolated frame needs ≈3.5x, a sustained 2x
  fires in ~0.5 s.
- Hysteresis: `active` outlives the last evidence by 5 s; `just_started` is the rising
  edge only. A scene that stays changed for 60 s is **adopted** as the new baseline
  (otherwise a nudged camera is a data bill forever).
* It is a **change detector, not an intruder detector**: it cannot tell a person from
  a car, a cloud shadow, or a light switching on. On `/vs1` (640x480) P-frames average
  451 B, so `min_delta_bytes` must drop to ~300 or the substream is blind.

### Recording

`<card>/rec/YYYYMMDD-HHMMSS.h264` (raw Annex-B, 4-byte start codes, SPS/PPS as the
encoder emits them) + `.json` sidecar written when the segment closes. 3 s pre-roll
(ring, flushed on the trigger), 3 s post-roll, 60 s max, **every file starts on a
keyframe**, 8 GiB quota with oldest-first eviction. A yank mid-write halts the recorder
with one log line instead of killing the process — this card has been pulled mid-write
once already.

### What is still missing

1. **The camera itself.** 192.168.1.103 has been unreachable (no ARP) since the last
   work; every number above is host-side. Nothing has run on the board yet.
2. **Wiring the uploader** into `main.rs` and a receiver at homelab.
3. **The encoder shim** — see `analysis/encoder-ownership.md`: the vendor
   `arm-anykav200-linux-uclibcgnueabi` crosstool (gcc 4.8.5, uClibc 0.9.33.2) **is**
   downloadable and **links against the board's own `libmpi_venc.so`** (verified on
   firefly). Two corrections to older notes: the stock `rtsp` binary does not import
   `ak_venc_*` at all (the encoder lives in `libapp_rtsp.so`), and
   `ak_venc_set_cfg_path` is **not exported** — parameters come from `struct
   encode_param`, there is no `venc.cfg` anywhere.
4. **Transport for the push.** No TLS stack exists on this board (no `libssl`, only
   `libcrypto.so.1.0.0`; crates.io unreachable). v1 assumes a private link — a
   WireGuard/tailscale tunnel on the site router — with plain HTTP inside it.
